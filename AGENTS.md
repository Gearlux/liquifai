# Liquify Mandates

- **Zero Boilerplate:** Application startup MUST automatically initialize **Loggair** logging and **Confluid** configuration. Users should never write bootstrap code.
- **Type-Safe DI:** Command function signatures define the dependency contract. Liquify MUST resolve dependencies from Confluid config by inspecting type annotations.
- **Bootstrap Lifecycle:** The 5-phase lifecycle (parse globals, init context, configure logging, load config, execute) MUST remain strict and sequential. Never skip or reorder phases.
- **Config Promotion:** If the first CLI argument is not a registered command, it MUST be treated as a config file path. This convention is non-negotiable.
- **`grammar.py` Is The Single Source Of Truth For The CLI Grammar (stdlib-only):** The global-flag vocabulary (`grammar.GLOBAL_FLAG_SPECS`) and the token classifiers (`stops_positional` / `looks_like_arg` / `looks_like_key`) are declared ONCE in `liquifai/grammar.py`. The parser (`core._parse_globals`), `--help` rendering (`core._show_help`), and completion (`completion.py` re-exports `GLOBAL_FLAGS` / `PATH_VALUE_FLAGS` / `SHELL_VALUE_FLAGS` / `GLOBAL_VALUE_FLAGS`) MUST all derive from it — NEVER restate a flag list or re-implement a token rule elsewhere (the pre-consolidation triplicate had already drifted: `--log-dir` / `--docs` / `--refresh-completions` were parsed and completed but missing from `--help`). New global flags are added to the spec table ONLY; `hidden=True` marks internal plumbing (e.g. `--refresh-completion-value`) excluded from help AND from the derived completion sets. Like `exceptions.py`, `grammar.py` MUST stay pure-stdlib so the fast path may import it. Pins: `tests/test_grammar.py` (incl. the help-lists-every-visible-flag drift pin and the stdlib-only source check).
- **Module Layout — core orchestrates, helpers own their domain:** `core.py` holds `LiquifyApp` + the phase orchestration (`run()` → `_route()` → help → `_prepare()` → `_execute()`, with `Invocation` as the routed phase-1 value); the override grammar/application lives in `overrides.py` (`parse_override_args` / `merge_overrides_into_fluids` / `accepted_override_keys` / `delete_dotted_key` / `expand_strings`); annotation-driven DI lives in `di.py` (`resolve_kwargs` / `deep_flow` / `confluid_active_context`). `core.py` keeps underscore-prefixed re-export aliases (`_deep_flow`, `_expand_strings`, `_confluid_active_context`, `_parse_override_args`, …) because EXTERNAL callers import them from `liquifai.core` (fluxstudio's graphio tests) — do not remove the aliases; new code imports from the owning module. Shell completion is the `liquifai/completion/` subpackage (see the fast-path mandate for the module split); the shared operation-wrapping helpers `tools.split_context_param` / `tools.graft_signature` are the ONE signature-surgery implementation used by BOTH `core.build_commands` (CLI handlers) and `tools.make_mcp_tools` (MCP tools) — never re-inline that logic. The provider-spec derivation is likewise single-sourced in `completion.tree._provider_spec` (serialize_app projects it, iter_completion_providers yields it).
- **Dropped Override Tokens Are Warned, Never Silent:** `parse_override_args` returns `(overrides, deletions, dropped)`; `_apply_overrides` MUST log one `logger.warning` per `dropped` token (a typo'd `lr 0.1` instead of `--lr 0.1` silently running a job on defaults is the failure mode this prevents). The warning fires even when no valid override is present. Escalating to a hard error (with a `--` escape hatch) is a candidate after a bake period — do not remove the warning path without user sign-off. Pins: `tests/test_override_grammar.py`.
- **DI Block Selection Is By Membership, Not Truthiness:** `di.resolve_kwargs` selects the config block for a `@configurable` param via `in`-checks — class-name key first, then param-name key, then (only when NEITHER key exists) the whole top-level config (the flat-config fallback, load-bearing for sonair-style flat YAMLs). A present-but-empty block (`Trainer: {}` or YAML-null `Trainer:`) means "construct with defaults" and MUST NOT fall through. Confluid's top-level broadcast via `materialize(..., context=...)` is orthogonal and still applies accept-listed top-level keys regardless of block. Pins: `tests/test_di_block_resolution.py`.
- **CLI Failure Contract:** In `run()`, a `LiquifaiError` or `confluid.ConfluidError` raised during phases 3–6 is an EXPECTED user-facing failure: render ONE clean `Error: …` console line, write the full traceback to the log at DEBUG, `sys.exit(1)`. Under `--debug` the exception PROPAGATES instead (full traceback). Any OTHER exception is a bug and must always propagate — never convert it to a clean exit. Missing-config keeps its dedicated message + exit 1. Pins: `tests/test_failure_contract.py` (+ the contract case in `test_flow_modes.py`).
- **Context Lives In A ContextVar:** `context._active_context` is a `contextvars.ContextVar`, NOT a module global — concurrent in-process embeddings (threads/async, e.g. an MCP server) each see their own context; `set_context(None)` clears it (tests). Mirrors confluid's ContextVar migration. Do not regress to a bare global.
- **App Discovery: Entry-Point Group First, Probe As Fallback:** Liquifai apps declare themselves in the `liquifai.apps` entry-point group (`[project.entry-points."liquifai.apps"] <name> = "pkg.cli:app"`, name == `LiquifyApp.name` == the binary name) — `completion.discover.declared_liquifai_apps` reads the group instantly and those names are NEVER probed. The subprocess probe (`--show-completion bash` + marker check) remains ONLY for apps that haven't opted in (e.g. sairen until its pyproject declares the group) — do not remove it while any workspace app lacks the declaration. Every NEW liquifai app MUST declare the entry point in its pyproject (with the standard explanatory comment; requires an editable reinstall to take effect). Pins: the entry-point-group tests in `tests/test_completion.py`.
- **Completion Fast Path Stays Stdlib-Only & Never Imports The App In-Process:** The `liquifai-complete` hot path (`_fast_complete.py` → `completion.engine.complete_from_tree`) reads only JSON caches and imports only stdlib (+ the `liquifai/completion/` package — EVERY submodule of it must stay stdlib-only at import time: `shells` wire protocol/templates, `cache` value caches + refresh policy, `tree` snapshot/refresh (confluid only lazily inside functions), `engine` hot path, `install` rc splicing, `discover` app discovery; `__init__` re-exports the full historical surface so `from liquifai.completion import X` keeps working). The old in-process `_<APP>_COMPLETE` env-var protocol was REMOVED (every installed wrapper calls `liquifai-complete`; it was dead code). It MUST NEVER import the app or confluid (except the lazy config-override branch) IN-PROCESS, nor run a user provider in-process. Dynamic positional values (`@command(..., completions={...})` / `app.set_completions(...)`) come from providers that run ONLY at refresh time (`--refresh-completions`, the opt-in background thread, or the detached lazy-refresh helper below) and are written to `~/.cache/liquifai/<app>.values/`; the fast path just reads that cache. The ONE side effect it may have is to **detach** a self-heal subprocess for a stale/missing value cache — STATIC or DEPENDENT (see below) — a separate process, never an in-process import, never blocking. A provider may hit the network/SDK, so **background (full) refresh is OFF by default** (opt in with `LIQUIFAI_BG_REFRESH`). Providers are best-effort: a raising provider is skipped and completion falls back to the `<name>` placeholder. The value-cache key derives from the CANONICAL command path (aliases collapse to their canonical sub-app) so an alias shares the same cache.
- **Dependent Positionals: Arity + Pre-Enumeration + Lazy Self-Heal:** A provider's REQUIRED-positional-arg count (`_provider_arity`) decides its kind: **0-arg → static** (one global cache); **1-arg → dependent** (receives a dict of the EARLIER positionals, e.g. `<version>` gets `{"name": …}`). At refresh, dependent values are pre-enumerated over the cross-product of the prior positionals' STATIC cached values (capped by `max_combos`) and cached per input-hash under `<app>.values/<key>/<hash>.json`. **Both kinds self-heal lazily.** On TAB the fast path reads the cache for the exact typed inputs AND, if that cache is missing or older than `DEPENDENT_REFRESH_TTL`, calls the `lazy_refresh` callback (`make_lazy_refresh_spawner`) which DETACHES `<app> --refresh-completion-value '<json>'` (throttled by `LAZY_REFRESH_THROTTLE`; opt out `LIQUIFAI_NO_LAZY_COMPLETE`). For a STATIC positional `inputs` is `{}` and the marker/target is the flat `value_cache_path`; for a DEPENDENT one it is the typed prior-positionals dict and the per-input `dependent_value_cache_path`. That helper (`run()` → `_maybe_handle_refresh_completion_value` → `refresh_one`) runs only the one targeted provider and writes the cache, so a NEVER-refreshed static positional (e.g. a freshly-added `run list <experiment>`) populates itself on the next TAB without a manual `--refresh-completions`, and new/changed/beyond-cap dependent values self-heal the same way. `refresh_one` stamps `changed_at` in the (dependent) per-input cache ONLY when the values actually changed; `complete_from_tree` then leads the candidate list with a transient `<<positional>-updated>` hint for `DEPENDENT_NOTICE_WINDOW` seconds so the user sees the background refresh took effect (change-only, `<…>`-formatted so `_filter_prefix` drops it once a real value is typed). Prefix matching is **case-insensitive** (`_filter_prefix` lower-cases both sides) so `helios<TAB>` finds `Helios_…`. Keep this when touching `serialize_app` (tree stores `{positional: {key, kind, depends_on}}`, `CACHE_VERSION` ≥5) / `iter_completion_providers` / `refresh_value_caches` / `refresh_one` / `complete_from_tree`'s `lazy_refresh` param.
- **Completion Words & Candidates Are Space-Safe:** A value with embedded spaces (`Helios Base Model`, `Test Script VB`) MUST survive as ONE token end-to-end, or positional counting breaks and the shell falls back to filename completion. Two transport paths into `liquifai-complete`, both quote-aware:
    - **bash → `$COMP_LINE` + `$COMP_POINT`** (the raw line + cursor). Bash's own `$COMP_WORDS` array splits on `$COMP_WORDBREAKS` (which includes space) WITHOUT honoring quotes or backslash escapes, so `"Helios Base Model"` / `Helios\ Base\ Model` is shattered — `${COMP_WORDS[*]}` cannot fix that no matter how it's joined. So the bash wrapper forwards `$COMP_LINE`/`$COMP_POINT` and `_fast_complete` re-tokenizes with `completion.words_from_comp_line` (quote/escape-aware, tolerant of an unterminated final quote). Requires the up-to-date wrapper — old installs must `liquifai-install-completions` + re-source (until then they degrade to the `COMP_WORDS` fallback, which shatters spaces).
    - **zsh (`${(F)words}`) / fish (`commandline -opc`) → `$COMP_WORDS`**, NEWLINE-joined, parsed by `completion.split_comp_words`. These shells' word arrays are ALREADY quote-aware, so this path is correct for them (and is the fallback for un-upgraded bash). `_fast_complete` prefers `COMP_LINE` when present, else this.
  Emitted candidates go through `completion.escape_candidate` (backslash-escape shell-specials; placeholders `<…>` left verbatim) so the shell inserts them as a single argument. Never re-introduce a raw `COMP_WORDS.split()`, unescaped candidate output, or a bash wrapper that relies on `${COMP_WORDS[*]}` alone — all silently break space-containing values.
- **`--docs` Is `--help` In Line Layout:** `--docs` renders the SAME code-extracted option docs as `--help` (one `confluid.get_hierarchy` source of truth) via `report.show_configuration(..., layout="lines")` — one option per line, greppable. Keep the two layouts data-identical; never let `--docs` extract differently from `--help`/completion.
- **Typed Exceptions — raise from `exceptions.py`, dual-inherit the builtin:** Every error liquifai raises MUST be a class from `liquifai/exceptions.py` (root `LiquifaiError`; `CommandDefinitionError` as `ValueError`, `UnknownOperationError` as `KeyError`, `UnsupportedShellError` as `ValueError`), never a bare builtin — dual inheritance keeps pre-existing `except ValueError:`/`except KeyError:` call sites working. `LiquifaiError` deliberately does NOT subclass `confluid.ConfluidError` (CLI-definition errors are not config errors), and `exceptions.py` MUST stay pure-stdlib so `completion.py` (the fast path) may import it. The PEP-562 `__getattr__` `AttributeError` stays builtin (import protocol). Pins: `tests/test_exceptions.py`.
## Releasing to PyPI

Tag-driven: bump `version` in `pyproject.toml`, then `git tag v<version> && git push origin v<version>` — `.github/workflows/release.yml` builds, verifies (twine strict + a clean-venv wheel smoke test run from a neutral cwd, since the repo root would shadow the installed package), and publishes via PyPI Trusted Publishing (OIDC `pypi` environment; one-time pending-publisher setup documented in the workflow header). Publish ORDER across the trio: loggair → confluid → liquifai (each depends on the previous being on PyPI). Once published, this is a PUBLISHED project per the workspace mandate: feature/fix PRs go on THIS repo (`main ← dev/main`), never bundled into taidal workspace PRs.

## Project Quality Gates
To run the full quality suite for Liquify, execute the following commands from the project root:

```bash
# From ~/source
isort --settings-file liquifai/pyproject.toml liquifai
black --config liquifai/pyproject.toml liquifai
flake8 --config liquifai/.flake8 liquifai
mypy --config-file mypy.ini liquifai
pytest --cov=liquifai --cov-report=term-missing liquifai/tests
```

**Note:** Always use the root `mypy.ini` for cross-project type checking, as it contains the correct `mypy_path` for all internal packages.
