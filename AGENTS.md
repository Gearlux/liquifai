# Liquifai Mandates

## Current state

- **What it is:** the app framework every workspace CLI is built on — `LiquifyApp` bootstraps Loggair + Confluid and injects config-resolved dependencies into command signatures by type annotation, so an app declares commands/operations and nothing else. Feature-complete; v0.1.0 is on PyPI and v0.1.1 (seven bug fixes — flat-config broadcasting for `Any`-annotated params, Rich-markup escaping in the error renderer, and five around CLI override delivery/precedence) is tagged-pending. It REQUIRES `confluid>=0.3.0` (for `accepts_key`/`accepts_broadcast`/`accepts_any_key`, imported at module level in `overrides.py`) — against an older confluid the package does not import at all, so confluid 0.3.0 must be on PyPI FIRST (see *Releasing to PyPI*).
- **One registration, two front-ends:** a `@app.operation()` pure operation becomes an auto-generated CLI command (`build_commands()` + the presenter/context hooks) AND an MCP tool (`tools.make_mcp_tools`) off the same signature; `@app.command()` / `@app.script_command()` remain the hand-written CLI-handler paths.
- **Positionals interoperate with `--flag` and `key=value`:** declared via `positionals=[...]` on `command` / `script_command` / `operation` (`build_commands` derives them from an operation's required params); the shared `walk` binds leading tokens IN ORDER as verbatim strings until `Token.stops_positional` fires. They land in `config_data` BEFORE overrides, so an explicit `--name` wins over the positional slot. A POSIX `--` makes every following token literal, so a dash-leading value (`seek -- -5`) binds.

## Mandates

- **Zero Boilerplate:** Application startup MUST automatically initialize **Loggair** logging and **Confluid** configuration. Users should never write bootstrap code.
- **Type-Safe DI:** Command function signatures define the dependency contract. Liquify MUST resolve dependencies from Confluid config by inspecting type annotations.
- **Bootstrap Lifecycle:** The 5-phase lifecycle (parse globals, init context, configure logging, load config, execute) MUST remain strict and sequential. Never skip or reorder phases.
- **Config Promotion:** If the first CLI argument is not a registered command, it MUST be treated as a config file path. This convention is non-negotiable.
- **Config Paths Resolve Through Confluid's Search Tiers:** every relative config path — a promoted script-command token or a `--config` value — goes through `confluid.resolve_config_path` (`./` → `./config/` → XDG dirs, namespaced by the app name that `run()` sets via `confluid.set_app_name(self.name)`; `liquify()`'s lazy-context branch sets it too). Resolution happens ONCE: `_route`'s promotion peek resolves before its `.exists()` gate, `_prepare` resolves the final `config_path` before storing it in `LiquifyContext` — so the context, the not-found error, and the "Loaded configuration from:" line all name the REAL file. Never add a second `.exists()`-probe chain; extend confluid's resolver instead. Side effect to keep in mind: promotion is eager — a positional token is consumed as a config when a matching YAML exists in ANY tier (including `~/.config/<app>/`), so a stale `~/.config/<app>/report.yaml` silently swallows `app run report` that meant `report` as a positional. That is now DIAGNOSABLE: the walk records the raw token on `Invocation.config_token`, and `core._log_promotion_source` reports every promotion at TRACE plus a non-CWD one at DEBUG. It logs from `_prepare`, NEVER from the router — routing is phase 1 and loggair is only configured in phase 4, so a `debug`/`trace` call at the decision site is silently dropped (verified). Pins: `tests/test_config_search_paths.py`.
- **`grammar.py` Is The Single Source Of Truth For The CLI Grammar (stdlib-only):** The global-flag vocabulary (`grammar.GLOBAL_FLAG_SPECS`) and the token classifiers (`stops_positional` / `looks_like_arg` / `looks_like_key`) are declared ONCE in `liquifai/grammar.py`. The parser (`core._parse_globals`), `--help` rendering (the Global Options block is rendered by `report.show_global_options`, called from `core._show_help`), and completion (`completion.py` re-exports `GLOBAL_FLAGS` / `PATH_VALUE_FLAGS` / `SHELL_VALUE_FLAGS` / `GLOBAL_VALUE_FLAGS`) MUST all derive from it — NEVER restate a flag list or re-implement a token rule elsewhere (the pre-consolidation triplicate had already drifted: `--log-dir` / `--docs` / `--refresh-completions` were parsed and completed but missing from `--help`). New global flags are added to the spec table ONLY; `hidden=True` marks internal plumbing (e.g. `--refresh-completion-value`) excluded from help AND from the derived completion sets. Like `exceptions.py`, `grammar.py` MUST stay pure-stdlib so the fast path may import it. Pins: `tests/test_grammar.py` (incl. the help-lists-every-visible-flag drift pin and the stdlib-only source check).
- **ONE Tokenizer, ONE Walk (`walk.py`, stdlib-only — 2026-07-26):** `walk.tokenize(argv)` is the FRONT of every command line: it consumes the POSIX `--` end-of-options separator once and marks each following token `literal` (never an option, never an override, never stops positional consumption) — the escape hatch that makes a dash-leading positional (`seek -- -5`) representable. `Invocation.remaining_tokens` carries `Token`s (NOT strings) so downstream phases can still tell an option from a literal; `walk.option_texts` / `walk.literal_texts` are the ONLY sanctioned way to split them, and `run()` inspects `option_texts` for `--help`/`--docs`/`--debug` so `app cmd -- --help` runs the command. An unclaimed literal gets its own `logger.warning` (same no-silent-drop rule as the dropped-override-token warning). `walk.walk_invocation(tokens, nav, resolve_config)` is the SINGLE descent to (sub-app, command, promoted config, positionals) — `router._AppNav` reads live `LiquifyApp` objects, `completion.engine._TreeNav` reads the serialized JSON tree, and the ONE legitimate difference (dispatch resolves the promoted config through confluid eagerly; completion defers so the hot path stays stdlib-only) is the injected `resolve_config` callback, never a forked loop. A value-taking global flag owns the next token INSIDE the walk (`--level run` is not the `run` command) while both tokens still reach `_parse_globals`. NEVER re-implement the descent inline — the previous hand-written copies drifted into a real bug (completion never resolved `./config/`-tier configs). Pins: `tests/test_walk.py` (incl. the two-Nav-adapters-agree pin).
- **Module Layout — core orchestrates, helpers own their domain:** `core.py` holds `LiquifyApp` + the phase orchestration (`run()` → `_route()` → help → `_prepare()` → `_execute()`, with `Invocation` as the routed phase-1 value); TOKENIZATION + the shared argv walk live in `walk.py`; GLOBAL-FLAG PARSING lives in `flags.py` (`parse_globals(tokens) -> GlobalFlags` + `bind_dimension_flags`, moved out of `core` 2026-07-26 — `core._parse_globals`/`._bind_dimension_flags` are GONE, and the historical 5-tuple return became the `GlobalFlags` record so `_prepare` stops positionally unpacking five values); the override grammar/application lives in `overrides.py` (`parse_override_args` / `apply_overrides` / `merge_overrides_into_fluids` / `delete_dotted_key` / `expand_strings`); the app-side adapter for the shared walk lives in `router.py` (`_AppNav` + `_resolve_promoted_config` + the stateless `route(app, argv)` FUNCTION — there is no router class, same rule as `completion_cli`); annotation-driven DI lives in `di.py` (`resolve_kwargs` / `deep_flow` / `confluid_active_context`). The nine underscore-prefixed `core` re-export aliases (`_deep_flow`, `_expand_strings`, `_confluid_active_context`, `_parse_override_args`, …) are **DEPRECATED, removal in v1.0**: they are served by a PEP-562 `core.__getattr__` that emits a `DeprecationWarning` naming the exact replacement import, NOT by plain assignments (a plain alias is invisible, which is why the old "keep them forever" note never converged). Liquifai's own source and tests import from the owning module — pinned by `tests/test_deprecated_aliases.py`, which fails if anything internal regresses onto the deprecated surface — so the v1.0 deletion is a pure EXTERNAL migration. Do not add a new alias; do not delete these until the external consumers are audited (see `TASKS.md`). (`_accepted_override_keys` was already REMOVED 2026-07-26 with the function it aliased — see the settability mandate.) ALL Rich help rendering lives in `report.py` — the per-command option table (`show_configuration`), the top-level command/group index (`show_command_index`), the Scope Dimensions block (`show_scope_dimensions` — what a named config's `!scope:KEY=VAL` blocks offer per dimension + the `default_scopes:` value a bare run picks, read from the RAW document via `confluid.discover_dimension_values` / `confluid.default_scopes`, the SAME walk `flags.bind_dimension_flags` binds the flags from; rendered only when a config path is known, nothing when the document declares no dimension — 2026-08-18), and the Global Options block (`show_global_options`); `core._show_help` is pure orchestration (header, usage line, the flow-vs-static branch) and NEVER builds a Rich `Table` inline. Shell completion is the `liquifai/completion/` subpackage (see the fast-path mandate for the module split); the Rich-using CLI glue that INTERCEPTS the completion flags (`--show-completion` / `--install-completion` / `--refresh-completions` / `--refresh-completion-value`) + the post-command cache refresh lives in the top-level `completion_cli.py` (NOT inside `completion/`, which must stay stdlib-only) — `core.py` calls its MODULE FUNCTIONS via thin same-named private methods (`_maybe_handle_completion_install` → `completion_cli.handle_completion_install(self, argv)`, …) kept so external/test call sites are unchanged. There is deliberately NO controller object in between: the former `CompletionController` forwarded five methods to those five functions and added nothing — do not reintroduce a pass-through class. The shared operation-wrapping helpers `introspection.split_context_param` / `introspection.graft_signature` are the ONE signature-surgery implementation used by BOTH `core.build_commands` (CLI handlers) and `tools.make_mcp_tools` (MCP tools) — never re-inline that logic. The provider-spec derivation is likewise single-sourced in `completion.tree._provider_spec` (serialize_app projects it, iter_completion_providers yields it). `liquifai/discovery.py` was DELETED 2026-07-26 — its `get_configurable_paths` duplicated `confluid.get_hierarchy_from_instance`, which `report.py` actually calls; do not resurrect a second instance walker. `liquifai/pipeline.py` was likewise DELETED — `ConfigPipeline` was a chainable class of three methods with two call sites and no state; config loading is two lines in `_bootstrap`, override application is the pure `overrides.apply_overrides`. **No stateless wrapper classes**: if a type holds one field and exposes one method, it is a function (`CompletionController`, `CliRouter`, and `ConfigPipeline` were all removed under this rule).
- **`@operation` Is The ONE Ops-Registration Path:** pure operations (dict-returning functions surfaced as auto-generated CLI commands via `build_commands()` + as MCP tools via `make_mcp_tools`) register ONLY through `@app.operation(...)`. The former `@app.command(presentation=...)` dual-mode was REMOVED pre-release (2026-07-14, before the first PyPI tag) — `command()` is purely the traditional CLI-handler decorator (`name`/`default`/`positionals`/`completions`); do not reintroduce a second path into `_operations`. Pins: `tests/test_operation_command.py`.
- **`liquifai/bridge/` — SDK bridge subpackage (PROVISIONAL, `liquifai[bridge]`):** it sits OUTSIDE the version contract — kept in this repo but opted into via the `liquifai[bridge]` extra (a contract MARKER: no requirements today, since the subpackage needs nothing beyond liquifai's core; a pip extra cannot make a dependency-free subpackage absent from the wheel, so the enforced part is the top-level export exclusion). `__provisional__` / `__extra__` are the machine-readable form of the notice. Rationale + the revisit condition (a second consumer) live in `docs/architecture.md` §6. Pins: the provisional-surface cases in `tests/test_bridge_group.py`. the declarative SDK-to-operations engine extracted from sairen. Module split mirrors the core mandate: `spec.py` (`P`, `ExposeSpec` + untyped `options`, `@expose`/`@custom`), `shaping.py` (stdlib-only result/parsing helpers incl. `record_to_dict`, `dry_descriptor`, `DEFAULT_ADAPTERS`), `policies.py` (`BridgeConnection`/`OpPolicy` Protocols, `PolicyContext`, `build_op_signature`, built-in `call`/`items` policies), `group.py` (`SdkBridge` + `Group`). HARD RULES: (1) **consumer-dialect code NEVER lands in liquifai** — an SDK's pagination vocabulary, wire shapes, or result-envelope conventions belong in a consumer-registered policy (`SdkBridge(policies=...)`) or adapter (`adapters=`), exactly like sairen's `MafListPolicy` + `resources` adapter; (2) **no `from __future__ import annotations` anywhere in the subpackage** — liquifai DI, confluid, and FastMCP introspect live annotation objects on synthesized signatures; (3) **registration is per-`SdkBridge`-instance state**, never a module global — two bridged apps in one process must not collide; (4) unknown policy/adapter keys fail at DECORATION time with `CommandDefinitionError`, never at first call; (5) the subpackage is **provisional** (single production consumer): keep it OUT of the top-level `liquifai` exports/`__all__`, and its API may change in 0.x minors without deprecation. Pins: `tests/test_bridge_group.py`, `tests/test_bridge_policies.py`, `tests/test_bridge_shaping.py` (fakes in `tests/bridge_fakes.py` — hand-rolled, never MagicMock).
- **An Override That Reaches NOTHING Is Warned — And CONFLUID Is The Judge (2026-08-10, supersedes the 2026-08-03 local heuristic):** the sibling of the dropped-token rule below, one step further in — the token PARSED fine, it just reached no node. The verdict comes from confluid's own delivery ledger, never from a local guess: when CLI overrides were applied (`LiquifyContext.cli_overrides`, stored by `_apply_overrides`), `core.run_command` wraps DI materialization in `confluid.collect_report()` and `overrides.warn_unused_overrides` warns for every override key the report lists in `unused` — BEFORE the command body runs, so a doomed multi-hour run gets its warning up front. The candidate spelling per key: a glob-headed override keeps its full key (`--**.lr` — a `'**'` block registers per leaf), a named dotted override is judged by its HEAD block (`--opt.lr` expands to a top-level `opt:` mapping), a bare override by the key itself. This REPLACED `_warn_unmatched_dotted_overrides` (deleted, with its `_GLOB_SEGMENTS` suppression list and `merge_overrides_into_fluids`' `_matched` return): the pre-materialization heuristic re-derived confluid's ADDRESSING model exactly as the deleted `accepted_override_keys` re-derived its accept-list, and was wrong twice — glob heads and multi-hop paths were reported "ignored" while the value landed. The report is also STRICTLY more capable: a BARE override no object accepts (`--max_pcaks 3` — a typo the old rule structurally could not see) now warns too. A command that materializes nothing registers no candidates, so the check degrades to silence, never to guessing; without CLI overrides the report machinery is not engaged at all (the default path stays zero-cost). The dotted message still names the working spelling (`--lr`), because a warning that only says "wrong" costs the user the same run. Do NOT downgrade to debug/trace — an override the operator typed and did not get is exactly the actionable condition `warning` is reserved for. Note the complement: `report.unused` does NOT cover a bare override that loses the position contest — that is `_move_cli_keys_last`'s job (next mandate) and stays. Confluid-side prerequisite: a leaf delivered by the nested-marker cascade satisfies its glob-registered spelling (`ConfigurationReport.mark_used` — found by this adoption; confluid CHANGELOG 0.3.0). Pins: the `*_dotted_override_*` / `*_bare_override_*` / `*_glob_headed_*` / `*_multi_hop_*` cases + `test_end_to_end_a_doomed_override_warns_from_the_real_run` in `tests/test_override_broadcast.py`.
- **CLI Overrides Are APPENDED In The Order TYPED (2026-08-13, supersedes the 2026-08-04 bare-keys-only rule):** confluid decides precedence by POSITION — one rule, document order, last spec wins, no specificity tiers — so the CLI's only lever is where its keys sit, and the contract is ONE sentence: *flags behave exactly as if their keys were appended to the end of the document, in the order typed.* `apply_overrides` → `_move_cli_keys_last` re-seats EVERY override key's top-level head (bare keys AND dotted-expanded heads) at the end, iterating in typed CLI order; a head mentioned twice seats at its LAST mention. **The mechanism may NEVER reorder flags relative to each other** — the previous version moved only BARE keys, which forced every bare flag after every dotted flag: `--lr 0.2 --Trainer.lr 0.1` produced 0.2 on Trainer in BOTH flag orders (measured 2026-08-13), and a dotted override whose block pre-existed in the document kept the block's EARLY position and silently lost to a later bare document key (`Trainer: {layers: 8}` on line 1 + trailing `lr: 0.9` + `--Trainer.lr 0.1` → 0.9, while the same flag WON when no block existed). Both are fixed by the uniform re-seat; the accepted trade is that re-seating a pre-existing block drags its unrelated keys' precedence with it (pinned as documented behaviour). Flag order now carries meaning — last typed wins where flags overlap — and order-INDEPENDENCE (specificity: longest pattern wins regardless of flag order) is NOT expressible by seating; if ever wanted, it is a confluid-side override channel, not a cleverer seat order. Do NOT ask confluid for a "CLI beats YAML" precedence tier instead: the absence of tiers is what keeps "why did my knob not take?" answerable from the effective document alone. Rationale: `docs/architecture.md` §4 → *Amendment: the CLI keys are appended in the order typed*. Pins: the seating group in `tests/test_override_broadcast.py` (incl. `::test_a_specific_flag_typed_after_a_bare_flag_wins_on_its_class`, `::test_a_dotted_override_wins_even_when_its_block_preexists_in_the_document`, `::test_reseating_a_preexisting_block_drags_its_unrelated_keys`) plus the original `::test_flat_override_beats_a_key_the_document_already_declares`.
- **Dropped Override Tokens Are Warned, Never Silent:** `parse_override_args` returns `(overrides, deletions, dropped)`; `_apply_overrides` MUST log one `logger.warning` per `dropped` token (a typo'd `lr 0.1` instead of `--lr 0.1` silently running a job on defaults is the failure mode this prevents). The warning fires even when no valid override is present. Escalating to a hard error (with a `--` escape hatch) is a candidate after a bake period — do not remove the warning path without user sign-off. Pins: `tests/test_override_grammar.py`.
- **`deep_flow` Takes The DOCUMENT (`context=`) — Broadcasting Is Not Ambient (0.1.1, 2026-07-29):** `di.deep_flow(value, context=<config_data>)` builds a document-shaped `Fluid` with `confluid.load(..., context=...)`, which is what applies the flat-config contract (a top-level key injecting into the same-named ctor param). Omit `context` and each Fluid is built in ISOLATION with a bare `flow()`, dropping every top-level key **silently** — `dataset:` -> `None`, `max_epochs: 3` -> the ctor default, the run looking configured. Both `run_command` and `_resolve_kwargs` pass `self.context.config_data`. The parameter is EXPLICIT and must stay so: `confluid.active_context` covers `!ref:` resolution for a bare `flow()` but NOT broadcasting (verified — a `flow()` inside `active_context(doc)` returns ctor defaults), so reading the ambient state would look right and silently do nothing. Scope is deliberate: the kwarg itself and the lists/dicts inside it get the context (they are document structure, and confluid's own `accepts_broadcast` gates what may actually be injected); an already-BUILT instance's `Fluid` attributes do NOT (they are not document nodes). `!lazy:` stays deferred either way. This regressed invisibly the moment consumers moved from per-verb CLIs (`def train(trainer: LightningTrainer)` — a configurable annotation, so DI already materialized with context) to one polymorphic runner (`def run(runnable: Any)`); the genericity itself disabled the branch. Pins: `tests/test_flat_config_broadcast.py` (incl. the executed without-context counterfactual and the `Any`-vs-class integration pair).
- **DI Block Selection Is By Membership, Not Truthiness:** `di.resolve_kwargs` selects the config block for a `@configurable` param via `in`-checks — class-name key first, then param-name key, then (only when NEITHER key exists) the whole top-level config (the flat-config fallback, load-bearing for sonair-style flat YAMLs). A present-but-empty block (`Trainer: {}` or YAML-null `Trainer:`) means "construct with defaults" and MUST NOT fall through. Confluid's top-level broadcast via `materialize(..., context=...)` is orthogonal and still applies accept-listed top-level keys regardless of block. **A CLASS-NAME block is NEVER hoisted into the synthesized marker's kwargs (0.1.1, 2026-08-04)** — `hoist_block=False` on that branch alone. `Trainer: {lr: 0.5}` is confluid's OWN addressed-block spelling, read out of the context document at its DOCUMENT POSITION; copying it onto the marker takes it out of the document, and a value with no position cannot lose the one precedence contest confluid runs — so it beat a later bare key, and every `--lr` override, unconditionally (measured: `materialize(Instance(Trainer, **block), context=doc)` → 0.5 vs `materialize(Instance(Trainer), context=doc)` → 0.9 on the SAME document). Same root cause as the `**kwargs` bare-key fix — liquifai writing into a marker's kwargs what the document should deliver — one layer over. The other two branches MUST keep hoisting: a param-name block (`widget: {size: 7}`) matches by class name or instance `name:` and a synthesized marker has neither, and the flat fallback IS the context already. Both directions are pinned, because "make the bare key win" would be a specificity tier by another name. Pins: `tests/test_di_block_resolution.py` (incl. `::test_a_cli_override_beats_a_class_name_block` + `::test_a_class_name_block_still_wins_over_an_earlier_bare_key`); rationale: `docs/architecture.md` §4 → *Amendment: a hoisted block has no position*.
- **Settability Is Confluid's Question — NEVER Re-Derive An Accept-List (2026-07-26):** "may this key set this attribute?" is answered by `confluid.accepts_key` (ADDRESSED writes — constructor params, settable properties, `__init__`-body slots, `**kwargs` targets) and `confluid.accepts_broadcast` (BARE cascading keys — the same list MINUS `@configurable(broadcast=False)` classes and `NoBroadcast[T]` params). `overrides.merge_overrides_into_fluids` maps the two CLI forms onto them EXACTLY: dotted `--<name>.<key>` (addressed at the Fluid whose YAML `name:` matches) → `accepts_key`; flat `--<key>` (broadcast) → `accepts_broadcast`. **A THIRD predicate gates the DELIVERY, and it is not optional (2026-08-03):** `confluid.accepts_any_key(cls)` is checked FIRST on the flat branch, and a target that answers True — a `**kwargs` constructor, i.e. no accept-list — is SKIPPED rather than written. Writing into `Fluid.kwargs` is confluid's ADDRESSED channel: what lands there becomes a CONSTRUCTOR ARGUMENT, while a bare cascading key becomes a post-init ATTRIBUTE (`Fluid._addressed_keys`, confluid `engine.py`). Writing every accepted key erased that distinction, and since a `**kwargs` class accepts EVERYTHING, every bare CLI override arrived looking as though the user had addressed it at that node — run identity reached a metric's constructor (`ValueError: Unexpected keyword arguments: run_name`, raised by torchmetrics from a call site nowhere near the config) and a dataset loader's `load_dataset` (where NOTHING raised — it silently became part of a cache key, the more dangerous half). The tell that this was liquifai's bug and not confluid's: a top-level YAML key stays BARE and has always landed as an attribute, so the CLI was the only front-end that promoted it, and a working config broke the moment `--run_name` was added. A skipped key is NOT dropped — `apply_overrides` already merged it into the document, so confluid's own broadcasting delivers it with the right provenance (verified end to end: the metric builds AND `metric.run_name` is set). Do NOT "fix" a `**kwargs` constructor failure by parsing the library's error message and retrying without the offending keys: that only catches libraries that VALIDATE (the loader case raised nothing), couples liquifai to N upstream error-message spellings, and re-runs a constructor that may already have had side effects. Pins: `tests/test_override_broadcast.py::test_flat_override_is_not_written_into_a_kwargs_targets_own_kwargs` + `::test_flat_override_still_reaches_a_kwargs_target_as_an_attribute` + `::test_flat_override_still_reaches_a_class_that_declares_the_key`. Requires `confluid>=0.3.0` (module-level import). The old local `accepted_override_keys` was DELETED — it diverged from confluid on four counts (a `**kwargs` ctor, `__init__`-body slots, and BOTH broadcast opt-outs, which a flat CLI override silently bypassed), and every divergence was a bug. NEVER reintroduce a local accept-list and NEVER read a `__confluid_*__` marker from liquifai; a new gate belongs in confluid next to the ones it joins. A Fluid whose target class can't be resolved has no accept-list, so it falls back to "the key is already in the YAML kwargs" (a deferred `!class:` marker stays overridable). The walker is cycle-safe (`id()` tracking) like its `expand_strings`/`deep_flow` siblings. Pins: `tests/test_override_broadcast.py` (opt-out + `**kwargs` + body-slot + unresolvable-target + cycle cases), confluid `tests/test_no_broadcast.py` (the predicates themselves).
- **CLI Failure Contract:** In `run()`, a `LiquifaiError` or `confluid.ConfluidError` raised during phases 3–6 is an EXPECTED user-facing failure: render ONE clean `Error: …` console line — with the message `rich.markup.escape`d (0.1.1), because it is untrusted text interpolated into a Rich MARKUP string and any bracketed run Rich reads as a style is otherwise silently eaten; the casualty was an install hint, `pip install 'myapp[extra]'` rendering as `pip install 'myapp'`, a WRONG command handed to the user. Escape the MESSAGE only — the `[red]` prefix must still style. Pins: the markup cases in `tests/test_failure_contract.py`, write the full traceback to the log at DEBUG, `sys.exit(1)`. Under `--debug` the exception PROPAGATES instead (full traceback). Any OTHER exception is a bug and must always propagate — never convert it to a clean exit. Missing-config keeps its dedicated message + exit 1. Pins: `tests/test_failure_contract.py` (+ the contract case in `test_flow_modes.py`).
- **Context Lives In A ContextVar:** `context._active_context` is a `contextvars.ContextVar`, NOT a module global — concurrent in-process embeddings (threads/async, e.g. an MCP server) each see their own context; `set_context(None)` clears it (tests). Mirrors confluid's ContextVar migration. Do not regress to a bare global.
- **App Discovery: Entry-Point Group First, Probe As Fallback:** Liquifai apps declare themselves in the `liquifai.apps` entry-point group (`[project.entry-points."liquifai.apps"] <name> = "pkg.cli:app"`, name == `LiquifyApp.name` == the binary name) — `completion.discover.declared_liquifai_apps` reads the group instantly and those names are NEVER probed. The subprocess probe (`--show-completion bash` + marker check) remains ONLY for apps that haven't opted in (e.g. sairen until its pyproject declares the group) — do not remove it while any workspace app lacks the declaration. Every NEW liquifai app MUST declare the entry point in its pyproject (with the standard explanatory comment; requires an editable reinstall to take effect). Pins: the entry-point-group tests in `tests/test_completion.py`.
- **Completion Fast Path Stays Stdlib-Only & Never Imports The App In-Process:** The `liquifai-complete` hot path (`_fast_complete.py` → `completion.engine.complete_from_tree`) reads only JSON caches and imports only stdlib (+ the `liquifai/completion/` package — EVERY submodule of it must stay stdlib-only at import time: `shells` wire protocol/templates, `cache` value caches + refresh policy, `tree` snapshot/refresh (confluid only lazily inside functions), `engine` hot path, `install` rc splicing, `discover` app discovery; `__init__` re-exports the full historical surface so `from liquifai.completion import X` keeps working). The old in-process `_<APP>_COMPLETE` env-var protocol was REMOVED (every installed wrapper calls `liquifai-complete`; it was dead code). It MUST NEVER import the app or confluid (except the lazy config-override branch) IN-PROCESS, nor run a user provider in-process. Dynamic positional values (`@command(..., completions={...})` / `app.set_completions(...)`) come from providers that run ONLY at refresh time (`--refresh-completions`, the opt-in background thread, or the detached lazy-refresh helper below) and are written to `~/.cache/liquifai/<app>.values/`; the fast path just reads that cache. The ONE side effect it may have is to **detach** a self-heal subprocess for a stale/missing value cache — STATIC or DEPENDENT (see below) — a separate process, never an in-process import, never blocking. A provider may hit the network/SDK, so **background (full) refresh is OFF by default** (opt in with `LIQUIFAI_BG_REFRESH`). Providers are best-effort: a raising provider is skipped and completion falls back to the `<name>` placeholder. The value-cache key derives from the CANONICAL command path (aliases collapse to their canonical sub-app) so an alias shares the same cache.
- **Dependent Positionals: Arity + Pre-Enumeration + Lazy Self-Heal:** A provider's REQUIRED-positional-arg count (`_provider_arity`) decides its kind: **0-arg → static** (one global cache); **1-arg → dependent** (receives a dict of the EARLIER positionals, e.g. `<version>` gets `{"name": …}`). At refresh, dependent values are pre-enumerated over the cross-product of the prior positionals' STATIC cached values (capped by `max_combos`) and cached per input-hash under `<app>.values/<key>/<hash>.json`. **Both kinds self-heal lazily.** On TAB the fast path reads the cache for the exact typed inputs AND, if that cache is missing or older than `DEPENDENT_REFRESH_TTL`, calls the `lazy_refresh` callback (`make_lazy_refresh_spawner`) which DETACHES `<app> --refresh-completion-value '<json>'` (throttled by `LAZY_REFRESH_THROTTLE`; opt out `LIQUIFAI_NO_LAZY_COMPLETE`). For a STATIC positional `inputs` is `{}` and the marker/target is the flat `value_cache_path`; for a DEPENDENT one it is the typed prior-positionals dict and the per-input `dependent_value_cache_path`. That helper (`run()` → `_maybe_handle_refresh_completion_value` → `refresh_one`) runs only the one targeted provider and writes the cache, so a NEVER-refreshed static positional (e.g. a freshly-added `run list <experiment>`) populates itself on the next TAB without a manual `--refresh-completions`, and new/changed/beyond-cap dependent values self-heal the same way. `refresh_one` stamps `changed_at` in the (dependent) per-input cache ONLY when the values actually changed; `complete_from_tree` then leads the candidate list with a transient `<<positional>-updated>` hint for `DEPENDENT_NOTICE_WINDOW` seconds so the user sees the background refresh took effect (change-only, `<…>`-formatted so `_filter_prefix` drops it once a real value is typed). Prefix matching is **case-insensitive** (`_filter_prefix` lower-cases both sides) so `helios<TAB>` finds `Helios_…`. Keep this when touching `serialize_app` (tree stores `{positional: {key, kind, depends_on}}`, `CACHE_VERSION` ≥6) / `iter_completion_providers` / `refresh_value_caches` / `refresh_one` / `complete_from_tree`'s `lazy_refresh` param. **Double-TAB force-refresh (bash only):** the age gate means a cache that is fresh-by-age but WRONG (an item deleted upstream) won't self-heal until `DEPENDENT_REFRESH_TTL` lapses. A repeated/second TAB fixes this: bash sets `$COMP_TYPE` (readline completion type) inside the completion function, the bash wrapper (`_BASH_TEMPLATE` + the alias helper) forwards it to `liquifai-complete`, and `shells.wants_forced_refresh` classifies the listing family (`63`/`33`/`64`, NOT `9`/`37`) as "force". `_fast_complete` passes `force_refresh` to `complete_from_tree`, which refreshes REGARDLESS of age (only the age gate is bypassed) and calls `lazy_refresh(key, inputs)`. The spawner's `LAZY_REFRESH_THROTTLE` marker STILL applies to a forced refresh — so hammering the double-TAB spawns at most one refresh per throttle window (ONE refresh per completion session, not one per keystroke); do NOT bypass the throttle for force. Still detached — the double-TAB shows the current cache, the NEXT TAB shows the corrected list. zsh/fish leave `$COMP_TYPE` unset (no signal → age-gated only); the wrapper change needs a `--install-completion` re-run. Pins: `test_wants_forced_refresh` / `test_force_refresh_bypasses_ttl_on_fresh_cache` / `test_force_refresh_static_positional` / `test_force_refresh_spawns_once_per_session` / `test_fast_complete_forwards_comp_type` in `tests/test_completion.py`.
- **Positionals Are Never Advertised As Flags; Flag Completion Is Type- And State-Aware (tree v6):** `serialize_app` EXCLUDES a command's declared positionals (`__liquifai_positionals__`) from `signature_paths`/`signature_flags` — a required positional (`version-create <name> <source_version>`) is advertised ONLY by its `<placeholder>`/cached-value hint, never as `--source_version`; `--help`/`--docs` mirror this by rendering a dedicated "Positional Arguments" block (`report.show_configuration(..., positionals=…)`, fed from `_show_help`) and dropping positional-rooted rows from the options. The `--flag` and `key=value` spellings of a positional still PARSE at runtime (the positional/`key=value`/`--flag` interop mandate is untouched) — unadvertised ≠ invalid — and a flag-supplied positional counts as FILLED for the hint. The tree also records `signature_bool_flags` (every spelling — collapsed + full path — of `bool`-typed flags, from the `get_hierarchy` type strings): `complete_from_tree` treats the previous token as a value slot (silent → shell filename fallback) ONLY for a value-taking command flag; a bool flag (`--append`), a global non-value flag (`--debug`), and the self-contained `--key=value`/`--key+`/`--key-` forms fall through to flag suggestions. Already-typed option keys (any override-grammar spelling, scanned after the command token) are dropped from the candidates; global flags are deliberately NOT dropped (`--scope` repeats legitimately). Bug context: sairen's `dataset version-create … --append <TAB>` used to complete FILES and re-offer consumed `--target_version`. Pins: the `_version_create_app` suite in `tests/test_completion.py`, the positional-block cases in `tests/test_help_with_config.py`, and sairen's `tests/test_completion_surface.py` (integration, real mounted app).
- **Completion Words & Candidates Are Space-Safe:** A value with embedded spaces (`Helios Base Model`, `Test Script VB`) MUST survive as ONE token end-to-end, or positional counting breaks and the shell falls back to filename completion. Two transport paths into `liquifai-complete`, both quote-aware:
    - **bash → `$COMP_LINE` + `$COMP_POINT`** (the raw line + cursor). Bash's own `$COMP_WORDS` array splits on `$COMP_WORDBREAKS` (which includes space) WITHOUT honoring quotes or backslash escapes, so `"Helios Base Model"` / `Helios\ Base\ Model` is shattered — `${COMP_WORDS[*]}` cannot fix that no matter how it's joined. So the bash wrapper forwards `$COMP_LINE`/`$COMP_POINT` and `_fast_complete` re-tokenizes with `completion.words_from_comp_line` (quote/escape-aware, tolerant of an unterminated final quote). Requires the up-to-date wrapper — old installs must `liquifai-install-completions` + re-source (until then they degrade to the `COMP_WORDS` fallback, which shatters spaces).
    - **zsh (`${(F)words}`) / fish (`commandline -opc`) → `$COMP_WORDS`**, NEWLINE-joined, parsed by `completion.split_comp_words`. These shells' word arrays are ALREADY quote-aware, so this path is correct for them (and is the fallback for un-upgraded bash). `_fast_complete` prefers `COMP_LINE` when present, else this.
  Emitted candidates go through `completion.escape_candidate` (backslash-escape shell-specials; placeholders `<…>` left verbatim) so the shell inserts them as a single argument. Never re-introduce a raw `COMP_WORDS.split()`, unescaped candidate output, or a bash wrapper that relies on `${COMP_WORDS[*]}` alone — all silently break space-containing values.
- **Closed `Literal`s For Rendering/Behaviour Knobs:** a parameter with a fixed small set of string values is typed as a `Literal`, never a bare `str` — `FlowMode`, `Presentation`, and `HelpLayout` (`Literal["table", "lines"]`, declared in `core.py` and mirrored in `report.py`, threaded through `_show_help` → `report.show_configuration` → `_render_positionals`). A bare `str` there silently falls through to the default branch on a typo. Workspace mandate; see CLAUDE.md → "Prefer Closed `Literal`s Over Bare Strings".
- **`--docs` Is `--help` In Line Layout:** `--docs` renders the SAME code-extracted option docs as `--help` (one `confluid.get_hierarchy` source of truth) via `report.show_configuration(..., layout="lines")` — one option per line, greppable. Keep the two layouts data-identical; never let `--docs` extract differently from `--help`/completion.
- **Typed Exceptions — raise from `exceptions.py`, dual-inherit the builtin; LIBRARY CODE RAISES, ONLY `run()` EXITS:** Every error liquifai raises MUST be a class from `liquifai/exceptions.py` (root `LiquifaiError`; `CommandDefinitionError` as `ValueError`, `UnknownOperationError` as `KeyError`, `UnknownCommandError` as `ValueError`, `ConfigNotFoundError` as `FileNotFoundError`, `UnsupportedShellError` as `ValueError`), never a bare builtin. **No `console.print` + `sys.exit()` inside a `LiquifyApp` method** — `run()`'s failure handler is the ONE place an exception becomes an exit code, so an embedding host (a server dispatching commands in-process) can catch instead of being terminated; `_bootstrap`'s missing-config and `_execute`'s unknown-command paths were converted 2026-07-26 and keep their exact console messages through that handler — dual inheritance keeps pre-existing `except ValueError:`/`except KeyError:` call sites working. `LiquifaiError` deliberately does NOT subclass `confluid.ConfluidError` (CLI-definition errors are not config errors), and `exceptions.py` MUST stay pure-stdlib so `completion.py` (the fast path) may import it. The PEP-562 `__getattr__` `AttributeError` stays builtin (import protocol). Pins: `tests/test_exceptions.py`.
## Documentation Structure

- **Per-Section Docs + Runnable Example Twins:** The README is a compact LANDING PAGE (intro, key features, quick start, installation, and a docs index table); every substantive topic lives in its own `docs/<topic>.md`, and every docs page has a runnable companion script in `examples/` (auto-executed by CI via the `examples/*.py` glob — standalone, zero-arg, exit 0). When a feature changes, update the topic's docs page AND its example in the same change; a new topic gets a new `docs/` file + example + a row in the README index. Exception: an INSTALLABLE example app (a subdirectory project like `examples/pypeek/` or `examples/linefit/` with its own pyproject) is deliberately OUTSIDE the CI `examples/*.py` glob — never flatten it into a top-level example script. It MAY still opt into CI by shipping an `examples/<app>/run.py` self-test (executed by the scaffolded `examples/*/run.py` CI glob) that subprocess-drives `python <app>.py <verb> …` — no self-install, no network — as linefit does; pypeek deliberately ships NO run.py because every verb needs the live PyPI API. Docs links in the README MUST be absolute GitHub blob URLs (`https://github.com/Gearlux/<project>/blob/main/docs/...`) because the README doubles as the PyPI landing page, where relative links do not resolve (the loggair precedent); links BETWEEN `docs/*.md` files stay relative. **Public docs are STANDALONE (user instruction 2026-07-14):** the README and `docs/` of a published project must never mention workspace consumer projects (navigaitor, streamstudio, matrainer, aisland, …) or corporate-specific names (helios, Keysight, sairen) — an external reader has none of that context. Describe consumers generically ("a visual editor", "an MCP discovery service", "my-app") and keep example values neutral. Mentioning a project's own DEPENDENCIES (loggair, confluid) is fine.

## Releasing to PyPI

Tag-driven: bump `version` in `pyproject.toml`, make sure `CHANGELOG.md` has a dated `[<version>]` section covering the release (Keep-a-Changelog format, like loggair/confluid; pre-1.0 minors may break — say so under **Breaking**), then `git tag v<version> && git push origin v<version>` — `.github/workflows/release.yml` builds, verifies (twine strict + a clean-venv wheel smoke test run from a neutral cwd, since the repo root would shadow the installed package), and publishes via PyPI Trusted Publishing (OIDC `pypi` environment; one-time pending-publisher setup documented in the workflow header). Publish ORDER across the trio: loggair → confluid → liquifai (each depends on the previous being on PyPI). **A dependency floor is part of the release, not an afterthought:** when a change here starts using a confluid/loggair API that is not yet on PyPI, that dependency must be released FIRST and the floor in `pyproject.toml` raised in the SAME change — otherwise a clean `pip install liquifai` resolves the old dependency and dies at import. Verify before tagging with the release workflow's own check: build both wheels and install them into a fresh venv from a NEUTRAL cwd (`python -m build --wheel`, then `pip install <deps>.whl <liquifai>.whl`, then `import liquifai`). The current floor is `confluid>=0.3.0` — NOT yet on PyPI, so v0.1.1 is blocked on the confluid v0.3.0 tag going first. Once published, this is a PUBLISHED project per the workspace mandate: feature/fix PRs go on THIS repo (`main ← dev/main`), never bundled into taidal workspace PRs.
